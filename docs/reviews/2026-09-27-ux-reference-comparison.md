# Key composer catalog UX reference comparison

**Scope.** Read-only review of the synthetic key-composer prototype on September 27, 2026, against the uncommitted baseline above `c73a82c`. The components are frozen for this review; only this report is added. The prototype uses fixture data and in-memory state only. It does not test real providers, Bifrost routing, or production behavior. No user study or usability measurements were available, so the priorities below are reasoned design recommendations, not measured UX scores.

**Local baseline.** The composer places demo controls before the model browser; the browser then stacks search/view controls, category tabs, provider/capability/more-filter controls, sort/group controls, active-filter chips, bulk selection and result counts. Results can render as cards or an 11-column table. The table includes several deliberately unknown fields and requires horizontal scrolling; Expert mode adds a persistent draft tray at desktop widths and a sheet on smaller screens. In the parent-confirmed screenshot pass, desktop 1280×720 puts the catalogue heading at y=538 and first model at y=580, leaving about 1.5 rows visible; the toolbar spans four rows with grouping alone on another row. At mobile 390×844, the first card starts at y=763, with no complete card above the fold; the toolbar wraps across four or more rows. No page-level overflow was visible and categories scroll horizontally. The tray's create action is visible at y=563. Provider-logo overlap is reported fixed and screenshot-confirmed by the coordinating reviewer. Capability icons are represented as wrapped controls. Model selection remains model-first, groups are a separate optional tab, and access routing is expressed through selected provider accesses.

## Prioritized gaps and recommendations

1. **Too little of the catalog appears above the fold.** The confirmed desktop and mobile screenshots show the first model starting near the bottom of each viewport; mobile has no complete card visible. Search, view settings, categories, three filter entry points, sort, grouping, active chips, select-all and counts stack before results. Keep search, category and one primary filter entry visible; place sort, grouping and display customization together in compact View options. Reduce explanatory/demo text in the initial browsing path. Linear's filters and display options offer a useful progressive organization ([Filters](https://linear.app/docs/filters), [Display options](https://linear.app/docs/display-options)).

2. **The table and draft tray compete for width.** Expert mode combines a wide catalog table with a 300 px persistent tray, while the table itself has an 11-column minimum width and horizontal scrolling. Prefer cards as the default browsing view; retain a compact table for deliberate comparison, with a short set of useful columns and optional columns disclosed on demand. On narrow layouts, preserve the existing draft sheet. Vercel AI Gateway's catalogue is a useful reference for a model-first search/filter/table sequence, but it can show pricing and performance values that this fixture does not have ([Browse models](https://vercel.com/ai-gateway/models)).

3. **Unknown values occupy too much visual weight.** Cost, latency, privacy, training, free-tier and release fields appear in the comparison table although most are Unknown or unavailable in this fixture. Keep those fields out of the default view until supported data exists; where shown, keep the explicit Unknown state and provenance. Do not substitute empty cells, zeroes or inferred claims. Vercel's table supports the comparison shape, not a reason to display empty Registry columns.

4. **Capability icons need a stable row and overflow treatment.** Keep provider/model logos and capability icons, following the Vercel catalogue’s compact provider and “+N” capability cues. Prevent icon wrapping from changing row height; cap the visible set and expose remaining capabilities through a clear “+N” affordance. Keep the accessible tooltip/detail with source, declared status and unverified execution; expose unknown values there without presenting them as negative claims.

5. **Selection context is split across surfaces.** Each model card has selection and a separate Accesses popover, while the tray repeats access controls and group/direct-origin badges. Keep the primary action unambiguous at the model level and make configured provider-access state visible when it affects whether the model can be included. Keep exact IDs and per-access controls in the existing detail/popover path. The chosen domain remains models first, optional groups second, with Bifrost-native routing constrained to selected accesses; this review does not propose changing those rules.

6. **View controls and active filters need a clearer distinction.** The current view controls alter layout/size/metadata, while filters alter which models are shown; their relative placement makes these different tasks feel like one toolbar. Group result-affecting filters together and present layout, grouping and sort as display options. Show active filters as removable chips and retain the selected-outside-results count, which protects draft selections when filtering. Linear documents this separation explicitly and persists display preferences independently from filters ([Display options](https://linear.app/docs/display-options), [Filters](https://linear.app/docs/filters)); persistence is optional here until there is a concrete need.

7. **Keep the existing component system and trim composition first.** Bifrost already vendors shadcn/Radix primitives. shadcn describes itself as open component code intended to be composed and customized, rather than a drop-in library to migrate to ([Introduction](https://ui.shadcn.com/docs)). Reuse those existing primitives and variants; no library migration or new dependency is recommended. A component library cannot resolve the hierarchy and width issues by itself.

## Reference readout

- **Vercel AI Gateway models:** strongest reference for a model catalog with search, modality/provider/capability filters and a comparison table. Its visible cost, latency and release data are richer than the local synthetic fixture, so copy its information order selectively rather than its full column set.
- **Linear filters and display options:** useful reference for progressive disclosure and for separating result filters from presentation controls. Its product-specific persistence and keyboard shortcuts are not requirements for this prototype.
- **shadcn/ui:** relevant as the already-used primitive vocabulary and composition approach, not as a mandate to migrate or redesign the components.

These references document product patterns; they do not prove that a proposed arrangement is best for Registry users. Validate the reduced toolbar, card/table defaults and capability treatment with representative administrators before treating them as settled.
