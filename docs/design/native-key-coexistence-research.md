# Coexistence des clés virtuelles natives — recherche

## Conclusion

Le Registry doit traiter les clés sans politique comme candidates au passage natif, puis laisser Bifrost authentifier la clé et appliquer ses limites et permissions. Une clé native valide sans politique Registry garde ainsi sa réponse et son routage natifs. Une politique Registry existante reste autoritaire : clé désactivée, binding périmé ou identité incohérente = refus fermé. Cette proposition précise le contrat ouvert dans la [spec V1](core-v1-spec.md); elle ne prouve pas encore l'ordre exact des hooks sur la cible stock.

## Ce que le code fait aujourd'hui

- `HTTPTransportPreHook` appelle `Snapshot.Prepare` et renvoie directement toute erreur; il transmet ensuite le jeton brut à Bifrost (`native/main.go:133-164`). Dans le contrat upstream épinglé, le `HTTPTransportPreHook` s'exécute après les middlewares d'authentification transport, tandis que `HTTPTransportPreAuthHook` passe avant (`core_schemas_plugin.go:173-180`). Cela ne prouve pas encore l'authentification Governance ni son ID de VK.
- `Prepare` identifie le jeton via SHA-256. Absence de binding et politique désactivée aboutissent toutes deux à `registry_policy_missing` (`internal/registry/runtime.go:132-160`; `internal/registry/config.go:504-509`).
- Pour `/v1/models`, le post-hook vérifie l'identité Governance, puis intersecte le résultat natif avec la politique Registry (`native/main.go:174-200`; `internal/registry/runtime.go:245-307`). Pour l'inférence, `CheckAttempt` bloque les modèles hors politique; `PostLLMHook` vérifie l'identité après l'appel fournisseur (`native/main.go:229-272`; `internal/registry/runtime.go:48-68`). La documentation du pilote confirme que la garde actuelle renvoie 403 aux clés sans politique (`STATUS.md:14`; `integration/isolated_models.py:339-345`).
- Le pont admin découvre toutes les VK natives par l'API Governance et découvre les modèles depuis les fournisseurs et leurs clés activées (`internal/admin/live.go:232-241,243-290`). Il marque les VK sans policy `managed=false`, sans leur attribuer de sélection; `PUT /api/workspace` refuse une adoption implicite et n'applique les changements natifs qu'aux policies déjà présentes (`internal/admin/live.go:413-443,554-602,626-647`).
- La création native obtient le secret une fois, puis persiste son empreinte dans la policy (`internal/admin/live.go:761-795`). Le readback relit le secret depuis l'API native et exige que son empreinte corresponde à la policy (`internal/admin/live.go:827-840`). Les secrets n'appartiennent pas au DTO workspace (`internal/admin/live.go:65-103`).
- L'application d'une policy réécrit les `allowed_models` calculés par Registry; elle conserve certains champs de ligne, poids, blacklist et clés provider, et vide l'accès de fournisseurs non sélectionnés (`internal/admin/live.go:733-759`). Le schéma Bifrost épinglé tranche les listes VK : `version` 2 (défaut) signifie liste vide = deny all, `["*"]` = allow all; `version` 1 rétablit liste vide = allow all. Dans les deux modes, `blacklisted_models` prévaut; `allow_all_providers` donne accès aux fournisseurs absents des lignes provider-config ([schéma épinglé](https://github.com/maximhq/bifrost/blob/fdeef8e3f31a3b18a61666ba49247d07bae3600a/transports/config.schema.json#L31)). Le DTO VK admin lit les listes, la blacklist et les clés mais pas `allow_all_providers`; le pont ne lit pas non plus la version sémantique (`internal/admin/live.go:109-139`). L'adoption doit intégrer ces réglages, ou refuser les cas impossibles à préserver; ne pas supposer que « Registry sélectionné » signifie « autorisé nativement ».

## Comportement proposé

La classification fiable utilise le résultat d'authentification natif et son `virtual_key_id`, pas seulement l'absence d'un hash Registry. Le jeton inconnu avant Governance ne prouve pas que la VK est inconnue : une VK gérée peut avoir été tournée ou son binding peut être périmé.

| Requête / état après authentification native | Résultat |
| --- | --- |
| Jeton invalide | Laisser l'authentification Bifrost produire son résultat natif; aucun passthrough Registry ne doit autoriser la requête. |
| Aucune credential cliente | Préserver le comportement Bifrost configuré. La fixture de validation utilise `enforce_auth_on_inference=true` sans bypass : cette option exige au moins une authentification sur l'inférence, mais peut accepter API key ou user token. L'installation ne doit pas modifier ce réglage natif implicitement ; les appels anonymes ou avec une autre credential restent un cas de coexistence à préciser. |
| VK native valide, aucun policy Registry pour son ID | Passage natif sans réécriture ni filtrage Registry; Governance garde budgets, activité, fournisseurs, modèles et routage natifs. |
| VK native valide, policy activée et hash conforme à l'ID | Garde Registry actuelle, puis intersection avec les permissions natives. Toute identité différente échoue fermé. |
| VK native valide, policy désactivée pour cet ID | Refus Registry; ne pas reclasser comme unmanaged. |
| VK native valide, policy existe mais hash/secret ne correspond plus | Refus fermé et action explicite de réassociation/rotation; ne pas perdre les restrictions Registry en passthrough. |
| Identité native absente ou contradictoire | Pas de succès Registry; refus fermé pour le chemin géré. Pour le chemin unmanaged, n'autoriser le résultat natif qu'après preuve que Governance a authentifié et filtré la réponse. |

**Passthrough n'est pas une authentification alternative** : ne jamais marquer le contexte comme authentifié, fabriquer un ID Governance, ou accepter une requête unmanaged avant validation native de la VK. Le plugin doit préserver les octets et en-têtes de la requête unmanaged, puis le résultat natif inchangé. La règle V1 confirme déjà que Registry n'est pas une source de permissions supérieure à Bifrost (`core-v1-spec.md:71,75`). La fixture d'intégration active `enforce_auth_on_inference=true`, comme le harness isolé (`integration/isolated_models.py:237-240`), pour mesurer le refus des credentials invalides ; ce paramètre de test ne constitue pas une modification autorisée de la configuration des utilisateurs.

## Seams à modifier / vérifier

1. **Moteur (`internal/registry/config.go`, `runtime.go`)** : distinguer « hash sans policy connue » de « policy liée à cet ID mais désactivée/périmée ». Ajouter une décision explicite pour un candidat unmanaged sans lui inventer de `View`; garder la validation stricte des credentials et des overrides provider.
2. **Adaptateur natif (`native/main.go`)** : remplacer le 403 immédiat pour candidat inconnu par un contexte candidat intact, puis classer à partir de l'identité Governance. L'upstream épinglé charge les built-ins puis les plugins configurés, trie par placement, et documente `PreLLMHook` en ordre d'inscription avant l'appel provider (`transports_bifrost-http_server_plugins.go:175-187,243-254,325-365`; `core_schemas_plugin.go:170-181,389-408`). `post_builtin` est donc le point d'intégration candidat pour que le `PreLLMHook` Registry lise l'identité stampée par Governance et bloque une policy inactive/périmée avant le provider. L'`HTTPTransportPreHook` reste dans sa phase dédiée avant `PreRequestHook`/`PreLLMHook`, donc il peut encore préparer/réécrire le corps des managed; le chemin unmanaged le laisse intact. La séquence exacte identity → Registry et le comportement brut d'alias doivent être confirmés sur le commit stock et par une requête isolée avant d'en faire une garantie.
3. **Workspace et adoption (`internal/admin/live.go`)** : garder la découverte (`managed=false`), proposer une action explicite d'adoption, relire l'état natif actuel de la VK et ses restrictions avant de créer le binding hash+ID. Initialiser la policy depuis le sous-ensemble déjà permis; montrer les pertes/gains prévus et refuser les données natives ambiguës. Ne pas appeler `applyVirtualKey` tant que cette base n'est validée. Les éditions ultérieures doivent intersecter la sélection Registry avec les droits natifs existants, et toute perte native hors UI doit invalider l'aperçu/readback.
4. **Preuve d'intégration (`integration/isolated_models.py`)** : le harness établit déjà la baseline native pour trois clés, puis vérifie deux policies et le 403 historique pour la troisième (`:228-230,267-287,322-345`). Réutiliser ce scénario : après activation du plugin, la clé unmanaged conserve mêmes IDs et restrictions natives; clé invalide reste refusée; deux managed restent distinctes; après adoption, seules les permissions natives préexistantes restent accessibles. Conserver l'absence d'inférence (`:398-401`).

## Inconnues avant implémentation

- L'interface upstream documente `HTTPTransportPreHook` après l'auth transport, et `PreLLMHook` avant le provider (`core_schemas_plugin.go:173-181`). Le code Registry actuel utilise `pre_builtin`; le placement `post_builtin` est le candidat pour lire l'identité Governance avant le provider, mais le source épinglé consulté ici ne contient pas l'implémentation Governance ni `SortAndRebuildPlugins`. Confirmer l'ordre identity → Registry et tous les chemins `/v1/models` dans le source Bifrost complet/trace d'intégration. Vérifier aussi `enforce_auth_on_inference=true` et l'absence de bypass anonyme.
- `/api/governance/virtual-keys` fournit-il toujours le secret complet lors de la lecture, ou le masque-t-il selon les permissions/version? Le code actuel sait échouer le readback si le secret manque; l'adoption doit pareillement s'arrêter, jamais stocker un jeton brut (`live.go:827-840`).
- Le schéma épinglé tranche les sémantiques des listes (`config.schema.json:31-35,954-976,3865-3885`), mais leur application réelle reste à confirmer par un test sur la version cible. `nativeVK` ne transporte pas encore `allow_all_providers` ni les quotas/limites provider, et le pont ne lit pas le réglage global `version`; le rapport local note que le cas « sans fournisseur natif autorisé » reste à valider (`STATUS.md:14`; `live.go:109-139`).
- Une clé native peut être modifiée ou tournée hors Registry. Il faut définir la réconciliation : détecter un binding périmé par ID + empreinte et demander réassociation explicite; ne jamais convertir silencieusement cette situation en unmanaged.

## Preuve minimale à réutiliser

Le plus petit contrôle déjà proche est `integration/isolated_models.py`: comparer la baseline native avant/après plugin, vérifier le refus d'une clé invalide, les deux catalogues managed distincts, puis ajouter l'adoption et refaire les mêmes listes; aucune requête d'inférence n'est requise. Le harness doit déplacer Registry en `post_builtin`, vérifier que les requêtes managed/unmanaged aux alias bruts gardent la sémantique prévue, et tester les deux versions de liste vide sur fixtures contrôlées. Les tests `TestProjectionIntersectionAndPrivacy` et `TestProjectionRejects` couvrent déjà l'intersection et les réponses invalides; les tests de moteur autour de `Prepare` couvrent les refus actuels (`internal/registry/registry_test.go:249-280,374-447`). Le pilote final a 44/44 contrôles mais ne couvre pas encore la coexistence unmanaged (`reports/native-v2.2.2-live/README.md:42`).
