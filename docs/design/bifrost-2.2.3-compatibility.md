# Compatibilité avec Bifrost 2.2.3

Vérification des sources le 24 septembre 2026. **2.2.3 est publié** sous le tag `transports/v2.2.3`, commit source `411d62b28b03b03bd3b4025b2cfab50af45f05f4`. Le tag Git lui-même est annoté (`fe2a68533589ea880f803108739480a4e6f47f63`). La release pinne `core v1.10.2` et `framework v1.7.4`; le module `transports` déclare Go `1.27.0`. Le dépôt du Registry qualifie Go `1.27.1` et compile le gateway et le plugin dans le même module. [Release officielle](https://github.com/maximhq/bifrost/releases/tag/transports%2Fv2.2.3) · [go.mod publié](https://github.com/maximhq/bifrost/blob/411d62b28b03b03bd3b4025b2cfab50af45f05f4/transports/go.mod) · [comparaison 2.2.2 → 2.2.3](https://github.com/maximhq/bifrost/compare/transports/v2.2.2...transports/v2.2.3)

## Changements pertinents

- Les fallbacks des règles de routage peuvent épingler une clé (`key_id` dans l’API, `provider_key_name` ou `key_id` dans `config.json`). Le format historique `provider/model` reste accepté. L’affinité de session conserve maintenant l’épingle avec sa route. La structure Go et la résolution de ces références changent; les scripts qui écrivent directement les règles de routage doivent être adaptés et vérifiés.
- La prise en charge des champs OpenAI Responses progresse (`async`, `output_schema`, `tunnel_id`) et les formes MCP/conversation/filtres structurés sont mieux relayées. Des types Go exposés changent : `ApprovalResponseID` devient `ApprovalRequestID`, et `Error` / `Conversation` deviennent des unions. C’est un changement de source pour les consommateurs Go concernés, tandis que la release corrige le décodage et le réencodage du format réseau.
- GPT‑6 gagne les points de cache; `gpt-6-sol` et `gpt-6-luna` acceptent `reasoning.effort: "none"`. D’autres corrections touchent notamment le filtrage des paramètres d’échantillonnage et les événements d’affinité.
- Pas de migration de base de données annoncée. Le code de chargement des plugins `transports/bifrost-http/server/plugins.go` ne figure pas dans les fichiers modifiés de la comparaison. En revanche `core/schemas` change (`Fallback.KeyID`, setter interne de clé épinglée) et la dépendance passe de core 1.10.1 à 1.10.2; framework passe de 1.7.3 à 1.7.4. Governance monte de 1.8.2 à 1.8.3, dont le changelog n’annonce que ces mises à jour de dépendances. Le contrat de hooks du Registry ne montre pas de changement source identifié, mais le graphe Go du plugin change.

## Effet sur le Registry

Le Registry ne configure pas les fallbacks/règles de routage Bifrost. Les nouvelles épingles de clés n’imposent donc pas de changement à ses alias, catalogue, publication `/v1/models`, adoption des virtual keys ou politique de gouvernance. Le diff ne modifie pas les handlers de gestion des virtual keys ni les routes de récupération de secrets; il modifie la résolution de noms de clés dans la configuration de règles de routage. C’est une conclusion de revue de sources, pas une preuve de compatibilité d’exécution.

`GET /api/version` existe dans cette release : `ConfigHandler.RegisterRoutes` l’enregistre avec les middlewares configurés et `getVersion` renvoie la variable `version` en JSON. Le panneau peut donc afficher la version effectivement compilée en appelant ce endpoint authentifié, au lieu de coder en dur `2.2.2`. [Implémentation officielle](https://github.com/maximhq/bifrost/blob/411d62b28b03b03bd3b4025b2cfab50af45f05f4/transports/bifrost-http/handlers/config.go)

## Qualification native et limites

La paire gateway 2.2.3 / Registry `e25de3d` a ensuite été compilée et qualifiée sur **Linux ARM64/musl, Go 1.27.1**, à partir du commit upstream exact et sans modification des sources Bifrost. Le chargement dynamique et les hooks passent, ainsi que **42/42** contrôles du catalogue par clé, **72/72** contrôles du plugin (installation par URL, persistance, copie de clé, assistant Chat Completions/Responses et mapping) et **19/19** contrôles d’adoption. Les fournisseurs et clés sont synthétiques; les preuves utilisent les mêmes empreintes binaires. `/api/version` renvoie bien `v2.2.3`. [Rapport, provenance et empreintes](../../reports/bifrost-2.2.3/README.md).

Cette validation concerne **la paire recompilée**, pas l’ancien `.so` 2.2.2 chargé dans un gateway 2.2.3. AMD64, les images officielles précompilées, l’inférence chez un fournisseur réel et une migration de production ne sont pas qualifiés. L’instance Docker existante et les binaires publiés `v0.2.0-rc.1` restent inchangés. Chaque nouvelle combinaison de version Go, OS, architecture, libc, modules ou options nécessite sa qualification selon [STATUS](../../STATUS.md) et [la procédure native](../BUILD.md).
