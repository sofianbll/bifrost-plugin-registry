# Bifrost Registry — React UI

## Pilote local actuel (24 septembre 2026)

Cette UI est maintenant servie par Bifrost 2.2.2 sous `http://127.0.0.1:8082/bifrost-registry/` dans le pilote **local**. Le catalogue lit les modèles et accès natifs de Bifrost (dont CLI PROXY, 25 modèles découverts) ; les groupes et clés utilisent `GET/PUT /api/workspace` avec `If-Match`, création de clé virtuelle native et relecture réelle de `/v1/models`. Le secret d'une nouvelle clé est montré une fois et n'est pas inclus dans le workspace. Publication et relecture affichent Verified, Drift ou Not verified selon le résultat. Le [rapport de 39 contrôles réussis](../../../reports/native-v2.2.2-live/workspace-live-report.json) comprend deux vrais chats HTTP 200 pour `gpt-6-luna` et `CLI PROXY/gpt-6-luna` ; il ne valide pas encore le client Hermes ni la production.

Le laboratoire reste une page **Planned** : aucune campagne n'est exécutée par cette UI. Les préférences restent en `localStorage`, sans synchronisation avec la configuration du plugin. Une métadonnée inconnue reste inconnue ; les capacités Chat/Vision concernent les requêtes chat et Responses, tandis qu'Image/Embedding gardent leurs endpoints propres. Les clés natives non gérées ne sont pas adoptées automatiquement. Les alias courts ambigus entre sources et les clés sans politique Registry restent bloqués. L'en-tête des clés a été corrigé et contrôlé à 320 px sans débordement horizontal ; la revue UX complète avec Sofian et le parcours Hermes restent à faire.

Depuis ce dossier, `npm ci && npm run build` construit le `dist/` à monter en lecture seule comme `ui_dir` du plugin, par exemple `.../registry-prototype/dist:/registry-ui:ro` avec `"ui_dir": "/registry-ui"`. Le build porte le chemin public `/bifrost-registry/`. Le gateway nécessite le [patch Bifrost 2.2.2 et le montage décrits dans BUILD.md](../../BUILD.md#construire-et-monter-la-nouvelle-ui-locale). `npm run check` vérifie la logique UI.

## Historique du laboratoire de prototype (23 septembre)

Les paragraphes suivants documentent le laboratoire et les données de démonstration **avant le branchement réel**. Le lecteur Newman et sa relecture n'impliquent pas une campagne active dans le pilote local.

The laboratory imports the pinned Bifrost Postman collection: **3,530 requests in 114 top-level folders**. All tests / Custom preserves a custom subset. Folder and request names, bodies, paths and inherited named assertions come from the source. One target selector stores exact access IDs; creator, provider, group and task filters narrow that selector, and unchecking an access excludes it. Preparation ends in a source request preview. It does not execute provider requests or rewrite arbitrary official tests for another model.

The Runs view accepts Newman JSON reports and shows messages, requests, responses, assertions and recorded lifecycle events when present. Imported reports remain in browser memory across navigation. **Open recorded loopback demo** uses real Newman 6.2.1 output from three official requests against an isolated local stub: two passes and one deliberate failure. Its responses are synthetic and establish no Bifrost/provider capability. Playback timing is a UI replay, not a live gateway connection. The native Bifrost monitor provides aggregate progress; individual request events require a runner bridge that is not implemented here.

Source regeneration: `node scripts/import-harness.mjs /path/to/provider-harness.json public/harness-catalog.json`. The pinned source revision and SHA-256 are recorded in the generated catalog. To recreate the demo report, install `newman@6.2.1` in a temporary directory and run `node scripts/record-harness-demo.mjs /path/to/provider-harness.json /absolute/path/to/node_modules/newman/index.js`. This recorder binds only to `127.0.0.1` and uses no credentials. Sources and limits are in [the UI references](../bifrost-ui-patterns.md#harness-and-plugin-boundaries).

For the archived local demo, run `npm ci` then `npm run dev -- --port 4173 --strictPort`. Open http://127.0.0.1:4173/. This dev mode is separate from the mounted Bifrost UI above.

In the historical demo, registry records and API responses were illustrative; locally imported Newman reports retained their recorded evidence. State was held in browser memory. View defaults in **Settings** persisted separately in localStorage. The proposed `config.json` export was a UI preference contract, not an import-ready plugin config or runtime synchronization. The `google` access ID in fixtures represented a simulated Google AI Studio access, not Vertex. Those demo reports used no gateway, credentials or production data. Sofian's final UX approval is still pending.

The React UI primitives in `src/components/ui/`, `src/hooks/`, `src/lib/utils.ts`, `src/globals.css`, and the Bifrost images in `public/` are copied from [Maxim AI Bifrost](https://github.com/maximhq/bifrost) commit `6493abd3d1422c9bfde95f242fd57b38e73ce881` (`ui/`). `globals.css` adapts Tailwind source scan paths and font URLs to the mounted base path; `textarea.tsx` drops the unused autosize variant and its dependency. `src/lib/constants/icons.tsx` keeps the upstream provider SVG definitions with a minimal theme-wrapper adaptation. These upstream files remain under the Apache 2.0 license in `LICENSE`. Geist font files have their separate SIL Open Font License in `public/static/fonts/OFL.txt`. The screens and fixture data in `src/App.tsx` and `src/demo.ts` are new prototype code. Exact source hashes and shell adaptations are recorded in `PROVENANCE.md`.
